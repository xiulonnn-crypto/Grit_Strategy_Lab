# Phase 0 因子库与工厂 UI 返工复盘

## 结论

本次 UI 验收对齐耗时偏长，不是因为页面复杂度本身不可控，而是验收方法一开始没有把批准 UI 稿转成“开写前可拒收”的执行矩阵。实现先追功能和局部样式，后续才逐项补齐结构、文案、控件和状态语义，导致每轮 review 都暴露一个新的偏差面。

用户后续复盘指出更准确的核心问题：开发完成后，`GRIT_Coder` 没有严格按 Trace Matrix 对每个 UI 验收项逐项签核；在未达到 100% 与 UI 稿一致时就通过交付。这属于验收流程提前放行，不只是实现偏差。

## 主要原因

1. **Trace Matrix 后置**：最初矩阵更多用于交付说明，没有在实现前冻结模块顺序、字段清单、弹层默认态、rail 样式、搜索筛选和响应式验收项。
2. **设计稿与 live 数据替换边界不清**：技术方案里的后端状态和 UI 稿里的前台文案没有先建立映射，运行态计数、阻塞原因、准入状态容易直接进入主表，造成与设计稿不一致。
3. **状态语义缺少横向一致性检查**：同一行里“阻塞”“来源”“准入”三列曾出现信息冲突，例如风险列说需要复核，而准入列又显示可调用。
4. **工程话术泄露到用户界面**：`NaN`、不填 0、缺失处理等实现语义直接出现在前台，对金融用户不够直观，也扩大了文案返工面。
5. **可见控件未被逐项验收**：配置弹层的左侧 tab、右侧信息、分组筛选、搜索框等视觉元素在早期没有被当作交互合同逐项验证。
6. **响应式验收不足**：桌面表格优先完成后，移动端列宽、自适应和横向滚动问题暴露较晚。
7. **截图目检闭环太晚**：单测、DOM 断言和构建通过先行，但最终截图的人眼比对、密度检查和条件状态覆盖没有作为第一轮交付门禁。
8. **开发后签核缺失**：Trace Matrix 没有被当作最终签核表使用，缺少 `PASS / FAIL / BLOCKED / NOT_CHECKED` 的逐项状态和统计，因此未签核项被误当作已完成。

## 已固化规则

- `GRIT_Coder` 新增 Design-Locked UI 100% Preflight：实现前必须冻结设计基线、内容架构、状态语义矩阵、业务文案闸门、响应式闸门和条件状态。
- `GRIT_Coder` 新增 Design-Locked UI Post-Implementation Acceptance：开发后必须逐项签核 Trace Matrix；只要存在 `FAIL/BLOCKED/NOT_CHECKED`，不得声明 100% 一致。
- `grit-review` 新增 UI 返工防漏 Gate：reviewer 可因后置矩阵、缺截图目检、假控件、语义冲突、工程话术、移动端溢出直接拒收。
- `grit-review` 新增 UI 验收流程自审 Gate：当用户指出验收未按矩阵执行时，必须归类为验收流程缺陷，输出逃逸类型和新增门禁，而不是只继续修页面。
- `TECHNICAL.md` 新增 UI 交付前冻结与语义一致性门禁：把本仓库的因子/PIT 页面推荐口径固化为 `可调用 / 审慎可调用 / 暂不可调用` 与 `无阻塞 / 需复核 / 源阻塞 / 时点缺口`。
- `TECHNICAL.md` 新增 UI 开发后 Trace Matrix 签核门禁：只有 `FAIL=0`、`BLOCKED=0`、`NOT_CHECKED=0`，才能声明 100% 一致。
- `AGENTS.md` 新增 design-locked route 规则：Trace Matrix 必须前置，并覆盖内容/状态语义、真实交互、桌面/移动截图和工程话术拦截。

## 后续 100% UI 验收清单

1. 开写前写 Trace Matrix，不接受交付后补矩阵作为 100% 依据。
2. 先把设计稿每个模块、字段、按钮、tab、筛选器、弹层默认状态映射到文件/selector/view-model。
3. 先定义 raw 状态到前台中文标签、颜色和说明的映射，检查相邻列不冲突。
4. 前台主舞台只用业务风险语言，不直接暴露实现规则。
5. 桌面和移动都截图，必须打开图片目检。
6. 弹层、筛选、搜索、开关、保存、dirty close、READY/WARN/BLOCKED 等条件状态必须实际触发。
7. 最终交付前回答：`Would reviewer refuse this?`，只要答案不是确定的 `No`，继续修。
